1 Why CapMesh?

The Problem

Every agentic application today hardcodes its tools, agents, and skills:

Without CapMesh (today)

from tools.github import GitHubReader
from tools.snyk import SnykScanner
from agents.langgraph import SecurityAgent

repo = GitHubReader()        # HARDCODED
scanner = SnykScanner()      # HARDCODED
agent = SecurityAgent()      # HARDCODED

Change any tool = change code, update tests, redeploy.

With CapMesh

binding = resolver.need("read a repository")
# -> GitLab, GitHub, Bitbucket — whatever is best

binding = resolver.need("security scan")
# -> Snyk, Semgrep — whatever is approved

binding = resolver.need("notify the team")
# -> Slack, Teams — whatever is configured

Swap tools = one registry command. Zero code changes.

What happens when requirements change?

ChangeWithout CapMeshWith CapMesh
Swap GitHub for GitLab2-3 days (code + tests + deploy)30 seconds (register new provider)
Upgrade Snyk to Semgrep1-2 days30 seconds
Restrict intern accessDays (middleware + ACLs)1 YAML field
Audit what tools were usedNot possibleAutomatic (every resolution traced)
Add new capability at runtimeImpossible without restartRegister + discover instantly

2 Design Principles

Capability-First

Consumers express WHAT they need, not WHO provides it. CapMesh discovers the best provider.

Framework-Agnostic

LangGraph, CrewAI, Strands, AutoGen, Semantic Kernel — all register and resolve through the same API. Framework is metadata, not contract.

Compose, Don't Replace

CapMesh sits alongside A2A, MCP, and Agent Skills. It doesn't replace them — it discovers which one to use.

Docker-Inspired Artifact Plane

Build, push, pull, tag, inspect — same mental model as Docker, but for agents, tools, and skills.

Deterministic Resolution

Highest semver wins. Exact contract match. No ML ranking in V1 — predictable and auditable.

Governance Built-In

Approval status, visibility, environment isolation, version pinning, immutable digests — all in the manifest YAML.

3 Architecture

Two-Plane Architecture

Artifact Plane (Docker-inspired)

Build, register, push, pull, tag, inspect. Manages the lifecycle of providers as versioned, immutable artifacts with sha256 digests.


Capability Plane (CapMesh differentiator)

Resolve, discover, bind. Maps capability needs to providers through a deterministic pipeline: find candidates → policy → version → select → bind → trace.

Resolver Pipeline (9 Steps)

1. Find candidates     — registry.providers_for(capability, contract)
2. Filter revoked        — governance status check
3. Health check          — cached health status (stub in V1)
4. Contract match        — exact contract version (v1 never matches v2)
5. Apply policy         — visibility, environment, status rules
6. Version constraint    — semver filtering (>=2.0,<3.0)
7. Select best          — highest semver among approved candidates
8. Build binding         — protocol-specific connection via adapter
9. Record trace          — full audit trail in SQLite

4 How It Works

Step 1: Write a manifest

A manifest is a YAML file describing what a provider offers, how to connect to it, and who controls it.

# Agent manifest — a security reviewer built with CrewAI
governance:
  status: approved
  visibility: public
  environment: [production, staging]
  labels:
    framework: crewai
interface:
  protocol: a2a
  endpoint: https://crewai-security.example.com
metadata:
  api_version: capmesh.io/v1alpha1
  kind: agent
  name: crewai-security-reviewer
  namespace: security
  owner: security-engineering
  version: "3.1.0"
provides:
  - capability: security.code.review
    contract: v1
    description: Review code for security vulnerabilities
requires:
  - capability: repository.read
    contract: v1
Key insight: The manifest says requires: repository.read — not "requires GitHub" or "requires GitLab." The specific tool is resolved at bind time.

Step 2: Build and register

$ capmesh agent build --directory ./my-agent/
Valid agent manifest
  Name:    security/crewai-security-reviewer
  Version: 3.1.0
  Digest:  sha256:3f9f55a43b3cf6fa...

$ capmesh agent register --file ./my-agent/manifest.yaml
Registered security/crewai-security-reviewer:3.1.0

Step 3: Agents discover and use capabilities

# Natural language
result = resolver.need("scan for security issues")

# Or exact capability ID
result = resolver.resolve(ResolveRequest(
    capability="security.code.review",
    contract="v1",
    caller=CallerContext(identity="my-pipeline"),
))

# Use the binding
print(result.binding.protocol)     # "a2a"
print(result.binding.connection)   # {"endpoint": "https://crewai-security.example.com"}
# Call the provider directly using A2A/MCP/REST protocol

5 MCP Server Integration

CapMesh does NOT replace MCP servers. It sits in front of them — telling agents which MCP server to use, based on capability, version, policy, and environment.

Today: MCP configs hardcoded

# Every agent has its own config
mcp_config = {
    "server": "github-mcp",   # hardcoded
    "tool": "read_file"       # hardcoded
}
result = mcp_client.call(mcp_config)

No central registry. No access control. No audit trail. Swapping = updating every agent's config.

With CapMesh: MCP servers registered

# Agent asks for capability
binding = resolver.need("read a repository")
# binding.connection = {
#   "server": "gitlab-mcp",
#   "tool_name": "read_file"
# }
result = mcp_client.call(
    binding.connection["server"], args
)

Central registry. Policy enforced. Audited. Swap by registering a new version.

The MCP server keeps running unchanged. CapMesh adds:

  • Discovery: Which MCP server provides repository.read?
  • Versioning: Which version should I use?
  • Policy: Am I allowed to use it?
  • Audit: Who used which MCP server, when?

6 Natural Language Discovery

Instead of memorizing capability IDs, agents describe what they need in plain language:

# These all resolve to the right capability:
resolver.need("read code from a repo")           # -> repository.read
resolver.need("scan for security vulnerabilities") # -> security.scan
resolver.need("notify the team")                  # -> notification.send
resolver.need("create a bug ticket")              # -> issue.create
resolver.need("deploy to production")             # -> deploy.execute
resolver.need("query the database")               # -> data.query

How it works

  1. Exact match — if the query IS a capability ID, use it directly (score 1.0)
  2. Keyword match — decompose query and capability IDs into words, match them (score 0.8)
  3. Synonym expansion — "notify" matches "notification.send", "repo" matches "repository" (score 0.5)
  4. Description match — capabilities have descriptions that are also searched
No LLM required. Deterministic. Fast. Auditable. The final resolution still goes through the same policy, versioning, and trace pipeline.

Three levels of specificity

resolver.resolve(request)    # Exact ID — strict, for production pipelines
resolver.need("...")         # Natural language — flexible, for agent workflows
resolver.discover("...")     # Explore — see ranked matches, for discovery

7 Security & Governance

"Dynamic loading means losing control" — This is backwards. Without CapMesh, developers hardcode whatever tools they want. With CapMesh, the platform team controls the registry. Dynamic loading WITH governance = control at scale.

Approval Workflow

governance:
  status: approved        # approved | deprecated | revoked
  • approved — resolvable by agents
  • deprecated — visible in search, excluded from resolution. Agents auto-fallback to next best.
  • revoked — completely blocked. Audit trail preserved.

Nothing runs without explicit status: approved. The platform team controls the lifecycle.

Environment Isolation

governance:
  environment: [production]     # staging caller CANNOT access this

A staging agent resolving database.query will never get production database credentials. Automatic. No firewall rules needed.

Visibility Controls

governance:
  visibility: private           # only the owner can resolve this
  # or: organization            # only same-org callers
  # or: public                  # anyone
LevelWho can resolveUse case
publicAnyoneShared tools and utilities
organizationSame org as ownerTeam-internal tools
privateOwner onlySecurity-sensitive scanners, secret tools

Version Pinning

# Agent config: only use scanner v2.x
result = resolver.resolve(ResolveRequest(
    capability="security.scan",
    contract="v1",
    version_constraint=">=2.0,<3.0",    # pinned
    caller=caller,
))

Even if v3.0.0 exists, the agent gets v2.x. Compliance team says "only scanner v2 in production"? One config line.

Immutable Versions

Once published, a version's content can never be changed:

$ capmesh agent register --file malicious-scanner.yaml
Error: security/scanner:1.0.0 already exists with a different digest

Same version + different content = rejected. The only way to publish new content is a new version number. Tamper-proof by design.

8 Runtime & Production

Deployment

# Option 1: CLI
$ capmesh server start --port 8080

# Option 2: Docker
$ docker run -p 8080:8080 -v capmesh-data:/data capmesh-server

# Option 3: Embedded (in your Python app)
from capmesh.registry import Registry
from capmesh.resolver import Resolver
resolver = Resolver(registry=Registry(), policy_engine=default_policy_engine())

How agents call CapMesh at runtime

import httpx

capmesh = httpx.Client(base_url="http://capmesh:8080")

# Discover and bind — no tool imports needed
resp = capmesh.post("/v1/resolve", json={
    "capability": "security.code.review",
    "contract": "v1",
    "caller": {"identity": "my-agent", "environment": "production"}
})
binding = resp.json()

# Call the provider using the returned binding
if binding["protocol"] == "a2a":
    result = a2a_client.call(binding["binding"]["endpoint"], task)
elif binding["protocol"] == "mcp":
    result = mcp_client.call(binding["binding"]["server"], task)
elif binding["protocol"] == "rest":
    result = httpx.post(binding["binding"]["endpoint"], json=payload)

Skill Dual Binding

When a Skill is resolved, CapMesh performs two bindings:

  1. Load skill — SKILL.md instructions + assets
  2. Resolve tool dependencies — each requires capability is independently resolved to a tool
# The skill says "I need repository.read" — not "I need GitHub"
# CapMesh resolves the tools separately
{
  "protocol": "skill",
  "connection": {
    "instructions": "SKILL.md",
    "tool_bindings": [
      {"capability": "repository.read", "provider": "gitlab-reader:2.0.0", "protocol": "mcp"},
      {"capability": "repository.search", "provider": "gitlab-reader:2.0.0", "protocol": "mcp"}
    ]
  }
}

Same skill YAML works with GitHub, GitLab, or Bitbucket — no changes needed.
